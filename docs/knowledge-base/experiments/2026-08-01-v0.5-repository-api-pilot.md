# v0.5 Repository API Pilot

日期：2026-08-01

## 目标

把 v0.4 的“给定 Repository Patch 后做可信验证”推进为真实闭环：模型读取受限的
仓库源码，生成候选修改；Direct 记录首次结果；Adaptive 在同一个首次候选失败时才调用
一次 Repair，并再次进入 Managed Docker 验证。

本轮只发送三个版本化 Benchmark 的实现文件、任务描述、候选修改和脱敏验证消息。
受保护测试、`.env`、API Key 和项目其他文件不进入模型输入。

## 固定配置

- 模型：`gpt-5-nano-2025-08-07`
- 定价记账：输入 `$0.05 / 1M tokens`，输出 `$0.40 / 1M tokens`
- API：Responses API，`store=false`，`max_retries=0`，reasoning effort `low`
- 输出：Strict JSON Schema `{files: [{path, content}]}`
- 执行：Managed Docker，无网络、非 root、只读文件系统、资源限制、强制清理
- 全程预算上限：`$0.10`

价格来源为 OpenAI 官方
[GPT-5 nano 模型页](https://developers.openai.com/api/docs/models/gpt-5-nano)。预算器不使用
cached-input 折扣，按普通输入价保守记账；每次调用前以完整 prompt 的 UTF-8 字节数和
最大输出 token 预留费用。

## 实现中发现的问题

### R1：让模型直接书写 diff 是错误的边界

首轮 Direct `0/6`、Adaptive `0/6`。失败集中在缺少 hunk 行号、无 diff、corrupt patch，
还未进入语义测试。模型不应同时负责业务修复和 Git diff 协议细节。

修复：模型通过 Structured Outputs 返回完整文件替换，确定性程序校验相对路径、拒绝
受保护测试，再用 `difflib` 生成 patch。

### R2：源文件无末尾换行

Frame Decoder 的模型修改语义正确，但原文件末行无换行，初版渲染器把删除行和新增行
粘在一起。修复为生成标准 `\ No newline at end of file` 标记，并新增真实
`git apply` 回归测试。

### R4：首次得到真实自愈链

Frame Decoder 的 Adaptive 首次候选只修复了零长度帧，仍保留
`len(buffer) <= expected_length`；Docker 验证失败后，Repair 将其改为 `<`，最终通过。
该运行共 7 次调用、费用 `$0.00280590`。

### R5：不配对比较不能归因

独立生成的 Direct 与 Adaptive 初始候选得到 `7/9` 和 `9/9`，但差异可能完全来自采样，
不能归因于 Repair。另一次 TTL 失败只是多写了 `repository_id/` 路径前缀。

修复：允许且只允许单层 `repository_id` 前缀规范化；实验改成同一个首次候选的配对设计。
R5 报告只保留在本地开发证据中，并因不能支持因果结论而不列入提交的最终证据。

## 最终 R6 配对实验

`repository-v0.5-api-pilot-r6` 使用 3 题 × 5 次重复，共 15 个共享初始候选：

| Strategy | Passed | Repair routes | Attributed calls | Attributed cost |
|---|---:|---:|---:|---:|
| Direct | 15/15 | 0 | 15 | `$0.00525650` |
| Adaptive | 15/15 | 0 | 15 | `$0.00525650` |

R6 真实只执行 15 次共享调用，实际费用 `$0.00525650`。策略表的成本是反事实归因，
不能相加当作账单。R6 所有首次候选都通过，因此 Adaptive 正确地产生 0 次额外调用。

按任务分层，两种策略均为 Calculator `5/5`、Frame Decoder `5/5`、TTL-LRU `5/5`。

## 能证明什么

- 仓库源码可以在隐藏测试不进入 prompt 的情况下生成受约束文件修改；
- 确定性边界能把结构化文件替换转换为可验证 Git patch；
- R4 证明失败候选、验证证据、Repair 和复验链路真实可达且成功过一次；
- R6 证明 15 个首次候选通过时 Adaptive 不会增加模型调用；
- 全程实际费用被硬预算控制，远低于 `$0.10`。

## 不能证明什么

- 三个人工 fixture、一个模型和 15 个配对候选不构成广泛统计结论；
- R6 没有失败样本，不能估计 Adaptive 对总体成功率的提升；
- R4 只有一次自然修复成功，不能声称稳定自愈率；
- 这些任务仍小于真实多文件依赖升级、并发和大型代码库 Patch。
- 当前输出协议要求模型返回完整文件，适用于小型 Fixture；对数千行文件可能增加输出
  成本、截断和无关改动风险。大文件支持需要经过精确旧内容匹配、指纹和原子应用校验的
  Search-Replace Block，并需单独评测。

因此简历与演示应表述为“实现并验证了可达的仓库级自愈闭环和成本门禁”，不能写成
“成功率提升 22.2%”或“节省 80% Token”。
