# v0.3 Hard Matrix and Repair-History Evidence

Date: 2026-07-28
Model: `gpt-5.4-nano`
Reasoning effort: `none`

## Question

Can Adaptive route a naturally failing stateful task into evidence-driven repair, and can
preserving prior failed attempts help a bounded repair loop escape a repeated wrong fix?

This report separates natural Adaptive execution from recorded-failure replay. Replay validates
one known repair branch; it is not counted as a natural success-rate sample.

## Natural Adaptive result

Source: [`adaptive-v0.3-hard-matrix-pilot.json`](../../../benchmarks/results/adaptive-v0.3-hard-matrix-pilot.json)

| Task | Success | Path | Calls | Tokens | Duration |
|---|---:|---|---:|---:|---:|
| Frame Decoder | yes | Direct | 1 | 728 | 5.14 s |
| Idempotent Ledger | yes | Direct | 1 | 1,070 | 23.62 s |
| TTL/LRU | no | Direct -> Repair | 5 | 9,407 | 30.42 s |
| **Aggregate** | **2/3** | mixed | **7** | **11,205** | **59.18 s** |

The TTL/LRU candidate used `OrderedDict` access order as if it were expiry order. Its purge loop
stopped when the LRU entry was still valid, leaving an expired MRU entry in the cache. The public
routing suite rejected the candidate and Adaptive performed real Critic/Coder calls, but the
bounded natural run still failed.

This establishes both halves of routing behavior in one small matrix: easy-enough hard tasks remain
on Direct, while a concrete state-machine failure enters Repair. It does not establish that Repair
will always self-heal.

## Recorded-failure counter-evidence

Both exact replays start from the saved natural TTL/LRU failure fixture and use the same replay
dataset fingerprint.

| Replay | Success | Calls | Tokens | Observation |
|---|---:|---:|---:|---|
| Prompt-only | 0/1 | 4 | 8,760 | Repeated the queue-head expiry assumption |
| Attempt-history aware | 1/1 | 4 | 9,967 | Scanned every entry and passed 6 hidden cases |

Sources:

- [`repair-replay-v0.3-exact-natural-prompt-only-failure.json`](../../../benchmarks/results/repair-replay-v0.3-exact-natural-prompt-only-failure.json)
- [`repair-replay-v0.3-exact-natural-failure.json`](../../../benchmarks/results/repair-replay-v0.3-exact-natural-failure.json)

The comparison is diagnostic, not statistical. Model calls are non-deterministic, and each arm has
only one run. The evidence supports the narrower statement that attempt history interrupted this
recorded failure cycle; it does not prove a general causal effect across models or tasks.

## Evidence boundary

- Three tasks are insufficient for a general benchmark claim.
- One run per replay arm is insufficient for confidence intervals or significance testing.
- The local Oracle validates registered contracts; it cannot infer arbitrary business semantics.
- JSON reports and per-task traces are the audit source of truth. Phoenix is an operational view,
  not the scoring system.
- A later statistical phase should pre-register repetitions, model configuration, stopping rules,
  and confidence intervals before spending additional API budget.
