# v0.2 Evidence-Driven Repair Closed-Loop

日期：2026-07-28
模型：`gpt-5.4-nano`，`reasoning_effort=none`
执行环境：Managed Docker V2

## 目标

验证以下链路是否真实成立：

```text
recorded Direct failure
  -> failure evidence preserved
  -> Critic diagnoses current candidate
  -> Coder repairs current candidate
  -> frozen public route passes
  -> independent hidden suite passes
```

任务为 `simulate_ttl_lru(capacity, events)`。它同时包含 TTL 边界、LRU 更新、
覆盖写入、零容量和异常契约，避免继续只使用 `add`、`fibonacci` 一类记忆型题目。

## R1：发现假阳性

R1 自然 Adaptive 运行产生了一个真实 Direct 缺陷：`evict_expired` 只检查
`OrderedDict` 的 LRU 队首，并错误假设 LRU 顺序等同于过期时间顺序。

公开路由正确捕获了失败：

```text
expected ['A', None, 'B', 'C']
got      ['A', None, None, 'C']
```

旧 Repair 连续两轮未修好，`internal_success=false`。但原隐藏集没有覆盖“已过期
条目不在 LRU 队首”，所以旧成功计算只看隐藏集时输出了 `success=true`。这条结果
被判定为假阳性并保留在
[`adaptive-v0.2-r1-false-positive.json`](../../../benchmarks/results/incidents/adaptive-v0.2-r1-false-positive.json)。

## 修复

1. 最终成功改为 `internal_success AND hidden_success`。
2. 每一轮 Critic 都接收当前候选和最新 expected/actual 证据。
3. 下一轮 Coder 从上一轮修复结果继续，而非重新从原始失败代码生成。
4. Critic 必须逐事件追踪首个分歧，检查状态更新、遍历与排序假设。
5. R2 增加不同于公开路由的隐藏场景：过期 MRU 条目位于未过期 LRU 条目之后。
6. 增加防回归测试：内部失败不能被覆盖不足的隐藏集洗白。

## Recorded Failure Repair Replay

为了可复现地验证 Repair 分支，实验固定使用 R1 的真实失败模式
[`ttl-lru-expiry-order-bug.py`](../../../benchmarks/fixtures/ttl-lru-expiry-order-bug.py)。
运行前先由 Docker 确认候选确实失败，再调用 Critic 与 Coder。

Critic 正确定位：

```text
LRU iteration order is not expiry order.
The cleanup loop stops at the first unexpired LRU entry,
leaving expired entries later in the OrderedDict.
```

Coder 将过期清理改为扫描并删除所有 `expires_at <= current_time` 的条目。

## 结论边界

- 已证明：失败候选、公开路由证据、逐轮诊断、代码修复和双重验收可以形成真实闭环。
- 已证明：简单成功路径仍保持一次模型调用。
- 未证明：Reflection 在广泛真实任务上的统计收益。
- 未解决：不存在明确可执行规格时的通用 Oracle 问题。
- 下一步需要扩展多个状态机、解析器、数据结构与多文件 Patch 任务，并重复运行。
