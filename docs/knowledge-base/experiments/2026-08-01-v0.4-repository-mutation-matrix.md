# v0.4 Repository Mutation Matrix

Date: 2026-08-01

## Question

Can the repository evaluation boundary distinguish a real repair from a plausible but
non-fixing edit across both a trivial task and a stateful boundary-sensitive task, without
calling an LLM?

## Preregistered data

- Dataset: [`repository-v0.4.json`](../../../benchmarks/datasets/repository-v0.4.json)
- Committed report:
  [`repository-v0.4-mutation-matrix.json`](../../../benchmarks/results/repository-v0.4-mutation-matrix.json)
- Dataset fingerprint: `cdc92d1bc87cef1f`
- Sandbox image:
  `python@sha256:57cd7c3a7a273101a6485ba99423ee568157882804b1124b4dd04266317710de`

The dataset binds every task to a complete SHA-256 fixture revision, protected test paths,
a tokenized test command, and at least two registered mutations.

## Matrix

| Task | Difficulty | Mutation | Expected | Observed |
|---|---|---|---:|---:|
| Calculator repair | Easy | arithmetic fix | pass | pass |
| Calculator repair | Easy | documentation-only non-fix | fail | fail |
| Chunked frame decoder | Hard | exact-boundary fix | pass | pass |
| Chunked frame decoder | Hard | documentation-only non-fix | fail | fail |

Result: **4/4 expected outcomes matched**.

The hard fixture contains an off-by-one condition that delays frames when the buffered
payload length is exactly equal to the declared length. Its protected tests cover split
headers, split payloads, zero-length frames, multiple frames, invalid hexadecimal input,
incomplete input, and maximum-size validation.

## Security checks exercised alongside the matrix

- Fixture copies are re-fingerprinted before patch application.
- Symlinks are preserved during copy and rejected rather than followed.
- Direct protected-test changes fail during Patch header validation.
- Rename/deletion parser bypasses fail during post-apply protected-file fingerprinting.
- Unknown or stale fixture revisions fail before candidate execution.
- Docker-unavailable execution returns a failed verification instead of host execution.
- Candidate workspaces are read-only and network-disabled in a named Managed container.
- No execution container remains after the release gate.

## Reproduce

```powershell
.\.venv\Scripts\python.exe -m pytest -q `
    tests\test_repository_docker_integration_v0_4.py `
    -k mutation_matrix
```

The full release gate is:

```powershell
.\scripts\test-v2-managed.cmd
```

It currently runs Ruff, 130 deterministic tests, and 8 Docker integration tests. Neither
command calls the OpenAI API.

## What this does not prove

This experiment validates the evaluator, trusted-fixture boundary, and mutation corpus.
It does not measure whether an LLM can generate the correct repository Patch, whether
Adaptive routing improves repository repair rate, or whether two tasks generalize to
real multi-file business repositories. Those claims require a separately budgeted,
repeated Direct-versus-Adaptive API experiment.
